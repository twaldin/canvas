# Canvas contracts

Interfaces every slice builds against. The API wire format and object model live in `schema/canvas-api.json`; this file covers what the schema can't express: sockets, environment, the Swift tile protocol, the mention context format, and ownership rules.

## Sockets

| Socket | Path | Speaks | Owner |
| --- | --- | --- | --- |
| Canvas API | `~/Library/Application Support/Canvas/canvas.sock` | `schema/canvas-api.json` | App |
| cmux browser subset | `~/Library/Application Support/Canvas/cmux.sock` | cmux v2 JSON lines, browser methods only | App (isolated, deletable) |

Both sockets are created with mode `0600`. The cmux subset lives on its own socket so it never shares method names with our API and can be removed in one step.

The Canvas API checks every request's params, and each `object.batch` op's, against the method's schema before it runs (`ApiRouter.checkParams`, from `ApiParams`, which `scripts/gen-clients.ts` generates from the schema): a param the schema doesn't list, or a required one missing (or `null`), is `invalid_params` naming the unknown and missing keys and every param the method takes, required ones marked. A `caller` is honored when it is a terminal tile on any open board, so an agent working on another board (`board`) is credited there (`createdBy`/`updatedBy`, `board.history`) as on its own; placing beside the caller applies only on its own board.

### cmux browser subset

Exactly what omp's cmux browser backend sends (`src/tools/browser/cmux/`), framed as cmux v2 JSON lines: requests `{"id","method","params"}`, replies `{"id","ok":true,"result"}` or `{"id","ok":false,"error":{"code","message"}}`. Surfaces are object ids: a terminal tile is the calling surface (`CMUX_SURFACE_ID`), a browser tile is a browser surface; workspaces are boards. Every browser result carries `surface_id`.

Surface and workspace ids stay `obj_…`/`brd_…` on the wire, which omp 18.3 accepts; omp ≤18.1's owner inspection (`surface.list` via its surface-observation module) requires UUID ids and is unsupported.

A page an agent is driving stays visible to WebKit for 60 s after its last command, even when its tile is offscreen, the window is minimized, in a background tab, on another Space, or covered, or the app is hidden: `document.visibilityState` is `visible` and `requestAnimationFrame`, timers and `IntersectionObserver` run as they would for a user. Window occlusion detection is off for the page, and while its tile can't show it the web view waits in `WebStage`, a transparent click-through window of its own that stays on screen (ordered in only while something waits in it). A page that was hidden gets up to 0.5 s to present a frame before the command runs, so the first command already sees it visible. Then the tile's normal detach/release policy resumes. `view.render` of a browser tile counts as a command: a page that isn't loaded loads (in the stage) and is waited for until the render's `timeoutMs`.

| Method | Params | Result |
| --- | --- | --- |
| `browser.open_split` | `url`, `surface_id` (caller), `workspace_id`, `focus` (ignored) | `surface_id`, `workspace_id`, `url`, `created_split`, `placement_strategy` — a browser tile beside the calling terminal |
| `browser.navigate` / `back` / `forward` / `reload` | `url` (navigate) | `url` |
| `browser.url.get` | — | `url`, `title` |
| `browser.eval` | `script` (page world) | `value`. A script that is one expression runs as the body of an async function (`await` works) and a promise it returns is awaited, as Chromium's `Runtime.evaluate` with `awaitPromise` does; anything else (statements) runs as a program whose completion value is returned, without awaiting. Neither is subject to the page's CSP |
| `browser.snapshot` | `interactive`, `max_depth` | `snapshot` text, `refs` (`e1` → `{role,name}`), `page` (`title,url,ready_state`, plus `text,html` when not interactive) |
| `browser.screenshot` | — | `png_base64` (one pixel per CSS pixel), `width`, `height` |
| `browser.click` / `dblclick` / `hover` / `focus` / `check` / `uncheck` / `scroll_into_view` | `selector` (CSS or snapshot ref `@e3`) | — |
| `browser.type` / `browser.fill` | `selector`, `text` | — |
| `browser.press` | `key` (`Enter`, `Tab`, `Shift+Tab`, a character, …) | — |
| `browser.scroll` | `dx`, `dy` | `scroll_x`, `scroll_y` |
| `browser.wait` | one of `load_state` (`interactive`/`complete`), `url_contains`, `selector`; `timeout_ms` | `url` |
| `surface.list` | `surface_id` or `workspace_id` | `workspace_id`, `window_id` (null), `surfaces` (`id`, `type`, `title`: a page's own `pageTitle`, else `title`; `url`) |
| `surface.close` | `surface_id` (browser only) | — ; `board.history` credits the terminal the connection opened splits from (`browser.open_split`'s `surface_id`), else the terminal that opened the tile |

The terminal a command comes from (its driver) is the one the connection opened splits from, else the one that opened the tile, else none. `board.history` credits a page's URL changes and the tiles it opens (`_blank`, `window.open`, ⌘-click) to whoever last acted on the page within 10 s (`NavigationCredit`): a driven command that can act (`navigate`, `back`, `forward`, `reload`, `eval`, element actions, `type`, `fill`, `press`) → its driver (`system` when none), the user clicking or typing in the page, its address bar, back, forward or reload → `user`; otherwise (a redirect or timer later on) `system`. A tile the user opened from a page is revealed (least pan) and selected; one an agent's command opened isn't. The same address opened again from the same page within 2 s gets the first tile back.

Error codes: `invalid_params`, `not_found`, `method_not_found`, `unauthorized`, `timeout`, `js_error`, `unavailable`. The plain-text line `auth <password>` answers `OK: …` or `ERROR: …`.

### Page log (console, errors, failed requests)

Every browser tile's main frame runs `PageCapture` (CanvasCore/PageLog.swift) in the page's own world at document start, so it sees the page from its first line on. It records console messages (`log` `info` `warn` `error` `debug`, as the console formats them, up to 1,000 characters; warnings and errors with the `url:line:column` of the code that logged), uncaught errors and unhandled rejections (message, source, stack), and failed requests: `fetch` and `XMLHttpRequest` answered 400 or more or never answered (network error; an aborted request isn't a failure), and elements whose resource failed to load (`img`, `script`, `link`…, from their `error` events; WebKit exposes no status for those). Errors and warnings go in one ring of 200, other messages in another of 200, so a chatty page never pushes out its errors; what falls out is counted (`dropped`). The tile hears nothing but the page's error count, at most once per 100 ms burst and 0 at every new document (message handler `canvasPageLog`, page world); everything else is read on demand (`__canvasPageLog.read()`, a non-enumerable, non-configurable global). The page's own document answered 400 or more is its first entry (`resource: document`, from the navigation response). Web vitals: LCP by `PerformanceObserver` (buffered) where WebKit has the entry type; CLS and long tasks (`layout-shift`, `longtask`, which WebKit lacks) are null and listed in `vitals.unsupported`; FCP, TTFB, DOMContentLoaded and load from the paint and navigation timings, null until they happen. Hooking `console` means the Web Inspector's console attributes messages to `canvas-page-log.js`; their stack traces still lead to the caller.

It also starts omp's cmux capture globals in the shapes omp installs after load, which omp then leaves in place: `__ompConsoleCapture` (`{entries: [{seq, ts, type: console|pageerror, level, text, args, location?, stack?}], nextSeq, dropped}`, 500 entries; `args` serialize when omp reads them) and `__ompCmuxResponses` (`{nextId, records: [{id, ts, method, resourceType: fetch|xhr, url, status, statusText, headers, requestHeaders, body, durationMs}]}`, 200 records, text bodies up to 64 KiB, none for streams or binary types). So omp's `tab.console()`, `errors()`, `requests()` and `waitForResponse()` cover the page's load. XHR is observed through `XMLHttpRequest.prototype` (`open`, `send`, `setRequestHeader`), not by replacing the constructor.

`object.get` on a browser tile adds `page` (schema `PageLog`): the counts since the page loaded, the latest 100 entries (after `since`, a `page.cursor` from an earlier call; one from an earlier document returns all of this one with `reloaded: true`), and the vitals; `loaded: false` when the tile has no page (released or never shown). The badge in the tile's address bar ("2 errors", only while there are any) opens a list of the errors, newest first (message, kind, `file:line`, time); a Hyper-click on a row stages a `console` mention (schema `MentionTarget`: `object`, the page's `url`, and the `entry`).

| `PYTHONPATH` | The app's `clients/python` (only the `canvas_sdk` package in a bundle), before an inherited value: `from canvas_sdk import canvas` works in every tile |
| `ZDOTDIR` | `extensions/shell/zsh`: zsh shell integration (below) |
| `CANVAS_ZSH_ZDOTDIR` | The user's own `ZDOTDIR`, only when the app's environment had one |
| `PROMPT_COMMAND` | `. <extensions/shell/bash/canvas.bash>` (before an inherited value): bash shell integration |
| `CANVAS_GHOSTTY_INTEGRATION` | Ghostty's shell-integration directory (libghostty-spm's `Ghostty/shell-integration`), unless the user's Ghostty config says `shell-integration = none` (`TerminalShellIntegration`). Interactive zsh sources `zsh/ghostty-integration` at the end of `_canvas_finish` (after the user's files, so a prompt framework's hooks run first; not when `_ghostty_integration_loaded` or real Ghostty's `_ghostty_state` is set); bash sources `bash/ghostty.bash` on `canvas.bash`'s first run and installs bash-preexec's hooks at once, so the first command is marked. Ghostty injects its integration only into shells it starts itself, and tiles run `sh -c … zmx attach … zsh -l`: without this there are no OSC 133 marks (jump to prompt, click to move, command exit status). |

Nothing else the app inherited reaches the shell except what a fresh login session starts with (`LoginSession`: `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_*`, `__CF_USER_TEXT_ENCODING`), `SSH_AUTH_SOCK`, `XDG_*`, and what Ghostty sets on the child (`TERM`, `TERMINFO`, `COLORTERM`, `GHOSTTY_*`): the zmx attach runs under `env -u` for every other inherited name. The app's environment is whatever launched it; launched from an agent's tool shell it held `CI`, `NO_COLOR`, `EDITOR=true`, `GIT_EDITOR=true`, pagers set to `cat`, and `CLAUDECODE` (Claude Code then refuses to start). The user's startup files set their own variables again, as in a terminal opened from the Dock.

Integrations report only when `CANVAS_ENV=1` and the variables they need are present, so they are no-ops outside the app.

Shell integration keeps Canvas's `bin/` first on PATH after the user's startup files, which may prepend directories (e.g. `~/.local/bin`, Claude Code's install location) that would shadow the wrappers. zsh: each startup file in `ZDOTDIR` sources the user's file of the same name with the user's `ZDOTDIR` in place (their files may set their own), and the last one zsh reads re-prepends `bin/`; interactive shells then restore the user's `ZDOTDIR` (unset if they had none), so shells they start are plain zsh. History stays the user's: macOS's `/etc/zshrc` runs while `ZDOTDIR` is Canvas's and points `HISTFILE` there, so before each user file a `HISTFILE` inside that directory moves to the user's `ZDOTDIR` (or `HOME`), and their own setting wins. A non-interactive login shell (a tile's `zsh -l -c '<command>; exec zsh -l'`, e.g. resuming an agent) keeps the integration for the command and the shell after it. bash: `canvas.bash` runs before the first prompt, after the user's startup files, as long as they keep an inherited `PROMPT_COMMAND` when setting their own; `bash -l -c` commands and other shells (fish, nushell) resolve `claude`/`codex` with whatever PATH their startup files leave. Before each prompt, interactive zsh (a `precmd` hook) and bash (`canvas.bash`) report the shell's directory as OSC 7 (`file://host/path`, percent-encoded, as macOS Terminal's own shell files do), which the tile keeps as the directory `path:line` references resolve against first.

zmx session names: `canvas-<tileId>`, labelled `canvas.board=<boardId> canvas.tile=<tileId> canvas.home=<support dir path, every byte outside [A-Za-z0-9._-] as _>` (zmx label values allow only those characters). `canvas.home` names the instance that created the session: board copies in another home (replicas, dev instances) carry the same ids, so `scripts/dev.sh stop` kills only sessions labelled with its own home. Because `zmx attach --labels` relabels a session that already exists, a tile never attaches to or ends a session labelled for another home (`TerminalTile.ownerGuard` runs before `attach` and `kill`): the copy's tile says whose session it is instead of taking it over. `scripts/dev.sh` trusts a `pid` file only while that process owns the home's socket, since a copied home carries the original's pid file. Names stay short because zmx sockets live under `$TMPDIR/zmx-<uid>` (a long `/var/folders/…` path for GUI apps) and a socket path is capped at 104 bytes. Tiles inherit the app's `TMPDIR`, so `zmx list` inside a tile shows canvas sessions. Deleting a terminal ends its session on every path (the UI close, `object.delete`, an `object.batch`, undo of its creation, redo of its delete): `Board.onTerminalsEnded` reports the terminals a step removed once its outermost step closes (a failed batch that put its delete back reports nothing), and the app runs `TerminalTile.killSession(tile:)` for each (owner-guarded). Undoing the delete brings the tile back with a new session (its `command`, or `omp --resume` for a recorded omp session).

## Agent integrations

Claude Code, Codex, Gemini CLI and opencode get omp's integration (`extensions/omp/canvas.ts`) through Canvas's wrappers `bin/claude`, `bin/codex`, `bin/gemini` and `bin/opencode`, one hook script (Claude Code, Codex, Gemini CLI) and one opencode plugin, `extensions/agent-hooks/hook.ts` (`run <claude|codex> <event>`, the agent's hook JSON on stdin). A wrapper execs the next `claude`/`codex` on PATH that is not a Canvas wrapper (any directory beside `extensions/agent-hooks`, so two Canvas installs never recurse), or exits 127 naming the missing binary. It adds the integration only when `CANVAS_ENV=1`, `CANVAS_TILE_ID` and `CANVAS_SOCKET` are set, `CANVAS_AGENT_HOOKS` is not `0` (the opt-out), and `CANVAS_AGENT` is unset; it then exports `CANVAS_AGENT=<kind>`, so an agent started inside that agent (and a second wrapper) runs plain and never reports as the tile's agent. Nothing is written to the user's agent config or repo.

- Claude Code: `claude --plugin-dir extensions/claude …`. The plugin holds `hooks/hooks.json` and `skills/canvas` (a symlink to the shipped skill, listed to Claude as `canvas:canvas`). Claude creates an empty plugin data directory `~/.claude/plugins/data/canvas-inline` the first time.
- Codex: `codex -c "hooks={…}" …`, printed by `extensions/codex/config.ts`. Codex skips non-managed hooks until their definition is trusted; the override is a session-flags config layer, whose `hooks.state` Codex honors, so it also carries `trusted_hash` for exactly the hooks it defines (key `/<session-flags>/config.toml:<event>:0:0`, hash as in codex-rs `hook_hash`). A Codex that hashes differently lists them under `/hooks` as needing review instead of running them.
- Gemini CLI: `GEMINI_CLI_SYSTEM_SETTINGS_PATH` pointed at a file `extensions/gemini/settings.ts` writes to `$TMPDIR/canvas-gemini/` (content-addressed): the user's own system settings file (the variable's previous value, else Gemini's default path) with Canvas's hooks appended (Gemini concatenates hook lists across its settings layers, so the user's settings and hooks keep working), `general.enableAutoUpdate`/`enableAutoUpdateNotification` off, and `hooksConfig.notifications` off unless the user has hooks of their own or set it (Gemini otherwise shows "Executing Hook: canvas-…" on every event). `GEMINI_CLI_SYSTEM_DEFAULTS_PATH` keeps pointing beside the user's system settings. Gemini 0.60 and later skip a system settings file whose directory isn't owned by root, so for those the wrapper runs Gemini plain (read from the real binary's `package.json`). Hook events: `SessionStart`, `BeforeAgent` (the prompt: `working`, tray drain as `additionalContext`, which Gemini escapes `<`/`>` in), `Notification` `ToolPermission` (`blocked` with the dialog's question, e.g. "Allow execution of: 'go'? (go version)", "Apply this change? (utils.go)"; the call is named by what it runs or changes, matched by `AfterTool`), `AfterTool` (`working`; follow: `read_file` with its `start_line`/`end_line`, `replace` at its first changed line, `write_file`, shell reads), `AfterAgent` (`idle`), `SessionEnd` (`agent.release`). Like Claude Code, Gemini runs no hook when the user presses Esc on or denies an approval or interrupts a turn: the tile keeps `blocked`/`working` until the next prompt.
- opencode: `OPENCODE_CONFIG_CONTENT` from `extensions/opencode/config.ts`: the user's own inline config (if any) with the plugin `extensions/opencode/canvas.ts` added to `plugin` (opencode merges it over the global and project configs and concatenates plugin lists), plus `OPENCODE_DISABLE_AUTOUPDATE=1`. The plugin runs inside opencode: `session.status` busy/idle → `working`/`idle` (idle debounced 250 ms), `permission.asked` and `question.asked` → `blocked` ("Permission required: bash go version", or the question; call `permission:<id>`/`question:<id>`), their `replied`/`rejected` → `working` with that call; `chat.message` (the user's prompt) → `agent.report_session` and the tray drained into a synthetic text part, which the model reads and the TUI doesn't show; `experimental.chat.system.transform` adds the awareness block; `tool.execute.after` → follow (`read` with `offset`/`limit`, `edit`/`multiedit` at the first changed line, `write`, `apply_patch`, shell reads). Subagent (child) sessions report nothing but their permission prompts, which opencode shows in the tile too. opencode fires no event as it quits: the plugin's process `exit` handler starts `agent-hooks/run opencode SessionEnd` (`agent.release`).
- Both take their integration from environment variables, which everything the agent starts inherits: the wrappers keep the user's value in `CANVAS_USER_<VAR>` and a nested wrapper (`CANVAS_AGENT` set) puts it back before running plain (`canvas_env_set`/`canvas_env_restore` in `wrap.sh`).

Only the tile's own session drives it (`extensions/agent-hooks/threads.ts`, tested with `bun test extensions/agent-hooks`). A subagent's events (`agent_id`: Claude Code's Task agents, Codex's `spawn_agent` threads, whose `session_id` is the parent's) report only its approvals (`PermissionRequest`) and finished calls (`PostToolUse`, no follow); its prompt, `Stop`, `SessionStart` and `SessionEnd` are ignored (Codex 0.155 fires `SubagentStart`/`SubagentStop` for spawned threads, Claude `SubagentStop`, which Canvas doesn't register). Codex's internal sessions (memory consolidation with `memories` on: ephemeral, `transcript_path: null`, `cwd` under `CODEX_HOME`) report nothing: they fire `SessionStart`, `UserPromptSubmit`, `PostToolUse` and `SessionEnd` with their own session id, which ended the tile's turn mid-answer, replaced its recorded session (resume broke), drained the tray into them and released the tile. Gemini CLI runs subagents as tools inside its main loop (`BeforeAgent`/`AfterAgent` fire once per turn), and the opencode plugin skips child sessions (`parentID`).

Reports carry `source: "canvas-claude"`/`"canvas-codex"` and `seq` = the hook process's start time in µs, so reports from hooks that finish out of order (async `PostToolUse`) apply in the order the agent fired them. Every call has a 1 s timeout and no reconnect wait, errors are swallowed, the process exits by 2.5 s, and without `bun` on PATH the hook does nothing: Canvas being gone never fails or stalls the agent. Resume: `claude --resume <sessionId>`, `codex resume <sessionId>`, `gemini --resume <sessionId>`, `opencode --session <sessionId>`.

Codex's `workspace-write` sandbox denies unix-socket connects (`EPERM`, which the CLI reports as `unavailable`), so the model's own `canvas` commands need escalated permissions; Codex offers no narrower grant than turning the sandbox's network on (`sandbox_workspace_write.network_access`, or a permission profile's `network.unix_sockets`, which enables all network), and the wrapper leaves the user's sandbox choice alone. The awareness block tells Codex to run canvas commands escalated. Hooks run outside the sandbox and are unaffected.

## Client connection

The Python SDK, TS client, and CLI find the socket in this order: an explicit value (`connect(socket=…)`, `new CanvasClient({ socketPath })`), then `CANVAS_SOCKET`, then `~/Library/Application Support/Canvas/canvas.sock` only if that file exists; otherwise they fail with `unavailable`, naming `CANVAS_SOCKET`, the path checked, and the explicit-connect fix. `caller` and `board` come from the client's own tile/board (explicit, else `CANVAS_TILE_ID`/`CANVAS_BOARD_ID` at construction). omp's `eval` Python kernel runs with an allowlisted environment that drops `CANVAS_*`, so the omp extension prints the explicit `connect(...)` line in the system prompt.

Connection failures are always `unavailable`; clients never surface raw socket errors. A socket file that exists but refuses this process (EPERM/EACCES, or ENOENT although the file is there: what Codex's seatbelt sandbox answers) fails at once, without waiting for the app, with a message naming the socket and saying a sandbox (e.g. Codex's) may be blocking it. A request that never left (connect failed, write failed, or its newline was unflushed when the connection closed) is sent once more on a fresh connection after waiting up to 15 s for the socket (an app restart). A request that left and lost its reply is not resent: `unavailable: … it may or may not have applied — re-read before retrying`. The exception is a read the schema marks `"resend": true` (`agent.wait`; generated as `RESEND_METHODS`): the client waits up to 15 s for the app to come back and sends it again with `timeoutMs` reduced by the time already spent, so a wait survives an app restart. Image methods (`view.render`, `view.snapshot`) take `out` as an absolute path the app writes (format by extension, png or jpg); clients resolve a relative `out` against their cwd. Without `out` the app writes a new file under `$TMPDIR/canvas-renders/` (`ApiRouter.scratchImages`, out of the user's repo); the result's `path` names the file either way, and images never travel inline.

The app writes replies and events through a per-connection queue, in order, and never blocks on a slow reader. An `events.subscribe` client that stops reading can't freeze the canvas; one that falls more than 32 MB behind is disconnected.

## Activity log

`board.history` reads `Board.activity` (`Sources/CanvasCore/ActivityLog.swift`): in memory, the newest 2000 entries per board, restarted with a `restart` entry when the app opens the board. Board mutations log themselves with their actor (`caller` → `agent:<tile>`, none → `user`, the app's own write-backs → `system`; undo/redo → `user`, prefixed `undo:`/`redo:`). Cascades of a change (a group re-fit to its members, an arrow end freed because its bound object was deleted) are credited to that change's actor and carry a `cause`; within one revision each object gets one cascade entry, amended to its net change (dropped when the changes cancel out), so a batch that moves or deletes 40 members of a lane logs the lane once. Bookkeeping (a terminal's lifecycle, session, title; a browser's `pageTitle`) is never logged. Follow re-aims log one `follow` entry, not the create/update beneath. The canvas reports viewport and selection changes continuously; the log records them once they have been still for 0.8 s and differ from the last logged state.

## Compositions

A composition is a module in a compositions directory. Functions whose first parameter is named `canvas` receive the connected client (all API namespaces plus `compositions`); other exports pass through unchanged. Python: `canvas.compositions.<name>.<fn>(…)`, `available()`, `reload()`. ## Object model rules

- Ids are prefixed: `brd_` board, `obj_` object, `men_` mention.
- `frame` is in canvas coordinates (points at 100% zoom) and is the whole box the object draws: a tile's includes its `RenderMath.tileTitleHeight` (26 pt) title bar at the top, and its content (the body, what `TileRenderRequest.size` and `contentSize` describe) is the frame below it (`RenderMath.body`). Measure, fit, groups, placement, `layout.*`, arrow attachment, and `view.render` pixel rects all use this one box. `z` orders siblings.
- Stored boards carry `format` (`Board.format`, 2). A board without it (format 1 stored a tile's body, its title bar drawn above) loads with every tile frame 26 pt taller, the same box on screen; saving writes format 2.
- `rev` increments on every change; `object.update` with a stale `rev` fails with `conflict`. The app's bookkeeping writes (`Board.writeBookkeeping`: a browser's `pageTitle`, the page's own title; `Board.reanchor`: a code tile's `range` and `anchor` re-found by content) leave `rev`, `updatedBy`, and `updatedAt` alone, but still take a board revision (`board.get since`), announce `object.updated`, and are saved.
- `createdBy`/`updatedBy` record the actor. An agent is identified by its terminal tile, on whichever board the object is.
- Deleting an object removes every staged mention that targets it, and its attention marker.
- Attention markers (`Board.attention`, one per object) are stored with the board until the user sees the object or someone clears them, and restored on open (markers on objects no longer there are dropped; `board.export` leaves them out). A marker belongs to its raiser's turn: when a terminal's lifecycle goes to `working` from `idle`, `done`, or no state (the user's next prompt reached it; blocked → working, an answered approval, and repeated `working` reports continue the turn), its markers are marked `earlierTurn`, and its next `view.attention` clears those (`cleared` in the result); markers from the current turn stay together. A raise without a terminal `caller` is never cleared that way. A terminal's own notification or bell (OSC 9, OSC 777 `notify`, BEL; `Board.raiseTerminalNotice`) raises a marker on that terminal with no `raisedBy`, unless the terminal has keyboard focus in the active window; the same message again, or a bell over any existing marker, changes nothing.
- Props a type doesn't define (`ObjectType.knownProps`, mirroring the schema's `*Props`) are kept, and `object.create`/`object.update` name each in `warnings`.
- A board belongs to one root directory; code paths are stored relative to it.
- `props.scale` (tiles and text shapes; `ObjectScale`, 0.25–8, absent = 1) magnifies the object's drawing inside its frame. A tile lays out at its natural frame (`CanvasObject.naturalFrame`, the frame ÷ scale; `RenderMath.body(of:)` is the natural body) and `TileFrameView` sets its bounds to frame ÷ scale, so title bar, content, hit testing, and mentions all work in natural points; renders draw the natural rect under the scale. A text shape's font is `DrawingStyle.textSize` × scale. What agents get is in canvas points: `object.measure` and `size: "fit"` (laid out at `width` ÷ scale, times scale), `layout.check` overflow, `view.render` `contentSize`/`overflow`, and line anchors (`CodeMetrics.lineY`). A mention's "over" region is in the host tile's own points. The user scales with ⌥-drag on a tile's corner, a text shape's corner, or Object ▸ Scale (Bigger ⌃⌘=, Smaller ⌃⌘- through `ObjectScale.step`'s levels, the presets, Actual Size ⌃⌘0; `CanvasView.setScale`/`stepScale`, on the selection, else the tile holding the keyboard); each changes frame and scale together (`ObjectScale.rescaled`: natural size kept) in one undo step, a tile placed by `Board.scaledFrame` (`refitFrame`'s rule: grown from its top-left when that covers nothing new, else up or left, else moved nearby, else in place), a text shape from its top-left. An `object.update` that sets `props.scale` with a size-only frame (`w`/`h`, no `x`/`y`) is placed the same way (`ApiRouter.scaled`), and says what it now covers in `overlaps` like any update. Liveness and zoomed-out handles use the effective zoom, magnification × scale.
- A group's `frame` is derived: its members' bounds (arrows excluded) plus `padding` and a `GroupSpec.titleHeight` title band, recomputed by `Board` in the same undo step as any change to a member's frame (nested groups outward), and on load. Frames written to a group are ignored. Stored groups labelled by the old `name` prop load with it as `title`.
- Placement (`Board.place`): an object created without a frame (an agent's, the follow tile, a pin, a link opened from a note or HTML tile) goes to the free slot nearest the caller's tile, touching it 24 pt away when there's room (right, then below, left, above), else nearest the viewport center; beside a tile, slots wholly (then partly) in view win over nearer ones out of it only within `Board.nearbyDistance` (600 pt, the gap between the frames) of the tile; further out the nearest free slot wins, in view or not, so on a busy board an agent's object stays by its terminal rather than landing in view beside someone else's (the agent raises a marker when the user should look); `place(_ ideal:)` finds the free slot nearest a given frame. An agent's own frameless creates (`object.create` without a frame or with `size: "fit"`, `browser.open_split`; `place(stacking: true)`) stack instead of going round the terminal: when the caller created a tile within `Board.answerStackWindow` (10 minutes) that is still on the board and isn't a follow tile, the free slot beside the newest such tile, by the same rules with sides ordered below, right, left, above, is taken if it touches that tile 24 pt below or right of it and is no less in view (wholly, partly, not at all, against the viewport inset 24 pt) than the slot beside the caller; otherwise the caller rule applies. Follow tiles, pins, links, and the user's objects never stack. Free means 24 pt clear of every tile and group, other agents' included; drawings and arrows never block. While the caller's tile (or the ideal spot) is on screen, a slot wholly inside the viewport (`Board.viewport`: the part of the window clear of the toolbar and tray, inset 24 pt) wins over a nearer one outside it, and when none fits, a slot partly in it wins over one wholly outside. A new follow tile (`place(width:height:near:shrinkingTo:)` with `Board.followMinimumSize`, 400×300, about 45 columns of code) may also be cut down to the part of such a slot that is in view: when no full-size slot fits wholly in view, a smaller one that does beats one partly outside (beside a default 1000-pt terminal in a 1976-pt view: 440×446 on its right, not 640×446 partly off-screen); a narrower sliver (198 pt in a 1492-pt view) keeps the full-size slot, since code wrapped at 18 columns is unreadable. The view never moves for it. Origins are whole points. The app places the user's own new objects by the same rule (`CanvasView.openForUser`: File › Open File, New Note, New Browser Tile, New HTML Tile, ⌘T, Go to's file rows at the viewport center; Edit Here's terminal beside its code tile), then pans the least that shows the object (`Layout.reveal`), selects it, and gives it the keyboard. API creates without a caller use the viewport center and never move the viewport.

## Layout

`object.measure`, `size: "fit"`, `layout.place`/`stack`/`translate`/`grid`, `object.batch`, and `layout.check` live in CanvasCore (`ObjectMeasure`, `Layout`, `Board.atomically`). Measured sizes are whole object frames, tile title bar included: code follows `CodeMetrics` (`ObjectMeasure.code`: as wide as the range's longest line up to the max width, `width` or `CodeMetrics.defaultFitWidth` = 960 pt, about 120 columns; longer lines wrap and count in the height; `layout.check` measures code at its frame's width), images (`LocalImage`: the picture at one point per pixel, at most `width` wide, default 960, plus the caption strip; an image created without a frame height is fitted like a note), notes (an `object.create` of a note without a frame height is fitted like `size: "fit"`, at `frame.w` or `ObjectMeasure.defaultNoteWidth`; `title` only names the tile) lay out `NoteRenderer` output with TextKit 2 at the note tile's own insets (`ObjectMeasure.note`, `noteInset`; `NoteRenderer`, `NoteLayout`, and `DrawingStyle` are in CanvasCore for this), text shapes use `DrawingStyle`'s font, and HTML pages are laid out by the app's WebKit (`ObjectMeasure.html`, set by the app to `HtmlTile.measure`: the page loads offscreen exactly as `view.render` loads it, in a throwaway tile 1 pt tall at the width, and its document scroll size once the kit reports `view.rendered`, at most 3 pages at once, 10 s each; `size: "fit"` gives `frame.w` or 640 and the title bar plus the document height, capped at `ObjectMeasure.maxHtmlFitHeight` = 4000; `layout.check` measures each HTML tile at its frame width, uncapped; CanvasCore alone reports HTML `unsupported`). Measuring reads files, so `object.measure`, a `size: "fit"` create/update, `object.batch`, and `layout.check` are resolved asynchronously; a batch measures every op first, then applies all of them synchronously inside `Board.atomically`, so no other request interleaves with its writes. `Board.atomically { }` is one undo step and one board revision; when its body throws, the changes it made are reverted (announced as normal changes, not recorded) and the error is rethrown. Layout ops move objects through one private `Board.shift` (groups by their leaf members, each object once) inside `Board.deferringRefits { }`, which holds group re-fits until the op's end and then re-fits each affected group once; group frames are stale only inside that scope. `size: "fit"` on an `object.update` without `frame.x`/`y` takes `Board.refitFrame`: grown from its top-left corner when that overlaps nothing it didn't already, else from the first other corner that doesn't (`Layout.refit`: top-right, bottom-left, bottom-right), else the free slot nearest the top-left-grown frame among those whose origin is within the frame's longer side of it (`place(_:)`'s rule, in view first, the object and its groups not blocking; `freeSlot(within:)`), else top-left anyway. Fitted results (and fitted batch ops, after the whole batch) carry `overlaps`, `Board.overlaps(of:)` by `layout.check`'s overlap rule, when not empty. Batch side effects stay per revision, not per op, in the app too: `avoid` arrows, whose routes depend on every tile, re-route once after a burst of changes (`ShapeLayer.rerouteAvoiding`: next main-queue turn or before the layer draws or renders), keeping the drawn route until then.

`layout.check` judges what is drawn: tile frames are whole tiles; arrows route with `BoardGeometry.routes(rows:)` (a value snapshot of the board taken when the call arrives, computed off the main actor) (line-bound ends by the model scroll rule, over each bound code tile's rows as it wraps them at its frame width: `CodeRows(file:width:)`); labels are placed exactly as the drawing layer places them (`DrawingStyle.arrowLabel` for the chip size, `DrawingGeometry.labelRect` against `BoardGeometry.blocksRoutes` objects, `BoardGeometry.labelRects`) and reported as `labelOverlaps` when they lie on a blocking object (their own ends included) or another label, each with the caption and the chip's frame (an arrow's own frame leaves its label out). The drawing layer re-places the labels of arrows whose label could sit where a tile or blocking shape came, went, or moved (`ShapeLayer.relabel`), so a label never stays under a tile that arrived after it and the check and the picture agree. With `ids` or `rect`, a crossing or label overlap counts when the arrow or anything it crosses or lies on is in scope (a new tile checked by its id reports the labels it covers); line-bound arrows whose ends lie within 300 pt of a scoped object have their tiles' rows read for it. Unfilled rects and ellipses are annotations (a box drawn around or across things): like ink and arrows they never take part in `overlaps`. A code tile's range compares its rows (`ObjectMeasure.codeRows`, wrapped at the frame's natural width in whole points, so a scaled fit tile's 611.99… pt is still its 612) with the frame and a taller range is `scrolls`, never `overflow`: code wraps at its width and scrolls to its range, so only its height can be short, and a fixed-height viewer usually means to scroll; a caption wider than the frame (`ObjectMeasure.captionWidth`, the header's own `CodeCaption.string` and `CodeMetrics.captionInset`) is `truncated`, not overflow; follow tiles (`followOf`) are fixed-size viewers and are skipped for both.

## Swift tile protocol

Every tile's content view conforms to `TileContent` (`Sources/CanvasApp/TileContent.swift`); `TileFrameView` supplies the shared chrome (title bar, drag, corner resize and ⌥-drag scale, lifecycle badge, zoomed-out card) and `TileFactory` maps an object type to its content view.

```swift
@MainActor
protocol TileContent: NSView {
    func setLive(_ live: Bool)                                  // false: detach heavy resources, show the card
    var liveZoom: CGFloat { get }                                // below this zoom the tile is its card (default 0.3; terminals 0.15)
    func render(_ request: TileRenderRequest) async -> TileRender   // offscreen image for view.render
    func cardSnapshot(_ deliver: @escaping @MainActor (NSImage?) -> Void)  // default: render at card scale
    func whenLiveReady(_ ready: @escaping @MainActor () -> Void)  // just made live: call once the live view is drawn (default: at once)
    func showSnapshot(_ show: Bool)                              // view.snapshot: cover Metal/WebKit content
    func mentionTarget(at point: NSPoint) -> MentionTarget?      // what a Hyper-click here mentions (element level)
    func outline(for target: MentionTarget) -> NSRect?           // hover highlight, in this view's coordinates
    var takesKeyboardFocus: Bool { get }                         // terminal, browser: true; code, note, HTML: false
    var surfaceLuminance: Double? { get }                        // what default-ink drawings over it contrast with (page background, image, terminal theme); nil: the app's own (default); post .tileSurfaceChanged on change
    var accessibleText: AccessibleTextElement? { get }           // VoiceOver's read-only text area while live: code lines (numbered), a terminal's screen; built only when asked (default nil)
    func update(_ object: CanvasObject)                          // a new revision of the backing object
}
```

`render` draws the content offscreen for `view.render`, independent of liveness, window, Space, and viewport: from the tile's model (or an AppKit view that draws itself anywhere, like a code tile's header, drawn offscreen), never by capturing what is on screen. `TileRenderRequest` = `size` (the body in points: the frame below the title bar), `scale` (pixels per point), `full` (the whole content, not the frame's window), `appearance` (resolve colors under it). `TileRender` = `image` (points, top-left at the body; `max(size, contentSize)` when full), `contentSize` (the content's extent at that width; overflow = content − size; a code tile's is its range, `CodeDocument.content`, which is what `size: "fit"` sizes), `state` (`rendered`, or `placeholder`/`failed` with a `reason`; never `rendered` with a blank image). The renderer cancels a render at the request's deadline (tiles should return what they have when cancelled) and reports a tile that still hasn't answered a second later as a placeholder. Tile chrome (title bar, border) is drawn around the image by the renderer; app chrome never is.

Zooming never redraws the scene: everything in the document (tiles, groups with their titles and borders, drawings, selection rings) is drawn in document coordinates and scales with the canvas, so its size relative to everything else never changes. Only window chrome (toolbar, tray, pills, edge pills), the dot grid, shape resize handles, selected tiles' resize handles, and attention markers stay screen-sized. A selected tile's handle (`TileHandles`) is a window-space view above `AttentionLayer`, so a marker ring never hides it; it takes no clicks: `TileFrameView`'s corner grip reaches under it, `TileHandles.reach` screen points past the corner, for every tile in a group or not. A marker's ring is its own view (`MarkerRing`) that pulses three times when the marker appears or its message changes; the bubble never fades. Bubbles keep off their object's header: `PillLayout.Marker.header` is the title bar plus `TileContent.headerHeight` (a browser's address bar, a code tile's header). Markers (`AttentionMarker`) live in `AttentionLayer`, a window-space view over the scroll view that passes clicks through except on a bubble; `CanvasView.layoutPills` places each around its object's on-screen rect, with the edge pills (`AttentionEdgeView`), on every bounds change (each pan and live-pinch step), so a marker tracks the zoom continuously and keeps its fixed size. Edge pills cover no tile (`PillLayout.place(... bands:)`): the nearest stretch of their edge clear of every on-screen tile, pill and prompt, else a chip in `CanvasView.chromeBands` covering the least tile area there, then nearest the ideal spot (the window controller's free parts of the toolbar row, left and right of the drawing toolbar, in window coordinates; none while the toolbar is hidden), else the earlier compromise on the edge. While `CanvasView.chromeHidden` (View › Hide Canvas Chrome) marker views are hidden and left out of placement; blocked terminals' are not. Cards are what the live tile shows: code cards draw the tile's own header view offscreen (`CodeHeaderBar.prepareForSnapshot`, its real controls) above rows drawn from the model at the tile's scroll; HTML cards are the live page's last capture. Going live, `TileFrameView` keeps the card over the content, which renders beneath it, until `whenLiveReady` fires (HTML: the page's first `view.rendered` after it attaches, once WebKit has presented that frame, `WebStage.afterNextPresentationUpdate`; browser: the page loaded and presented), at most `TileFrameView.revealLimit` (2 s).

Arrows, shapes, and groups have no tile; the canvas draws them.

Tiles never read or write the board store directly; they go through the board model on the main actor, which persists and broadcasts events.

### Code navigation

Code views get language features by conforming to `CodeNavigationHost` (`Sources/CanvasApp/CodeNavigation.swift`) and attaching a `CodeNavigation(host:board:tile:accessories:reservedWidth:)`:

```swift
@MainActor
protocol CodeNavigationHost: AnyObject {
    var navigationPath: String { get }                           // board-relative path of the file shown
    var navigationView: NSView { get }                           // the view showing rows; its coordinates are the host's document coordinates
    var navigationLineHeight: CGFloat { get }                    // row height, so panels open below the hovered line
    func sourcePosition(atViewPoint point: NSPoint) -> (line: Int, character: Int)?  // point in navigationView; 1-based line, 0-based UTF-16 column (a wrapped line's continuation rows map past the break); nil on peeked base rows/gutters
    func reveal(line: Int)                                       // scroll a 1-based line into view
}
```

The controller adds a hover tracking area to the view only while `setActive(true)` (hosts deactivate it when the tile goes not live: tracking areas on hidden tiles are rebuilt on every frame of a pan), handles ⌘/⌥⌘-click and right-click on it through an app-level event monitor (Hyper stays with `HyperMonitor`), extends the view's own `menu(for:)` rather than replacing it, and places an Outline button in the host's header (`accessories:`), inside the trailing `reservedWidth` points the host keeps free (`CodeHeaderBar.reservedTrailing`). Hosts call `contentChanged()` when they scroll or show new content, which dismisses hover and panels.

- **Outline** lists `LSPSymbol.outline`: every top-level symbol and the members of modules, namespaces, classes, enums, interfaces, structs and objects, never what a function or method holds (its locals). Its panel (`NavigationPanel.filterList`, shared with Find References and a list of several definitions) takes the keyboard, because the user asked for it: a filter field narrows the rows to names containing the text, ↑/↓ move the highlight, Return reveals it, Esc closes; closing gives the keyboard back to whoever had it (a terminal through its own focus path, `CanvasView.returnKeyboard`) unless something else took it. Hover panels never take it.
- **From the keyboard** (Code ▸ Go to Definition ⌃⌘J, Open Definition in New Tile ⌃⌥⌘J, Find References ⌃⌘R, Outline ⌃⌘O, on the focused code tile, else the one selected, else the one last clicked (`KeyboardFocus.codeTarget`), and with none a notice says there is no code tile to act on; `CodeTile.navigate`): no pointer names a symbol, so they act at the rows' selection, else at the first name on the tile's first range line (else its top row) that isn't a declaration keyword (`CodeSubject.firstName`: `write_usage` in `    def write_usage(self, …):`).
- **Find References** lists the references, each line once (servers list a line twice, e.g. a re-export's two names), in a filter list like Outline's that takes the keyboard (↑/↓, Return, Esc; ⌘↩ is Open All); a row opens that one (`Board.openForNavigation`, see Navigating to code). The list's **Open All** lays out every reference as a code tile (`Board.openExcerpts`): the reference line with 3 lines of context either side (clamped to the file), captioned "Reference N of M to `name` · L…", measured like `size: "fit"`, stacked top to bottom (a new column past 2400 pt) in a group titled "M references to name" in the free slot nearest the tile (`Board.place(near:)`); one undo step; the canvas pans the least that shows the first reference.
- **Without a language server** (`CodeNavigation.textFallback`: `LSPError.unavailable`, `unsupportedLanguage`, `startFailed`, `serverExited`; a timeout or the server's own error is shown as it is): Go to Definition, Find References and Outline answer from text (`TextNavigation`, CanvasCore). The search root is the board root for a file under it, else the repository holding the file (`searchRoot`). References: `git grep -n -z --column -w -I -F --max-count 60 --untracked -e <name>` (`--no-index --exclude-standard` outside a repository) through `GitRunner`, at most 200 matches (`truncated` says there were more). Definition: the same word matches filtered to lines that declare the name (`declarations(inLine:pathExtension:)`), ranked this file, then its language family, then the rest (`rankDeclarations`). Outline: `TextNavigation.outline` (tree-sitter `SyntaxSymbol`s with their `kind`, minus anything nested in a function, plus unindented pattern declarations on lines no symbol starts on). Every such list is titled as text search ("no language server") and carries the server's error as its one-line `note` (`NavigationPanel.filterList(note:)`).
- **Workspace symbols** (`LanguageService.workspaceSymbols`, `workspace/symbol`): one request per language and project root among the given files, starting servers as needed; a project whose server is missing or fails adds nothing. Go to asks with the files the board's code tiles show, else the first file of the language most listed files are in.

### Navigating to code

`Board.openForNavigation(_ aim: CodeAim, from source:, preview:, extra:)` (CanvasCore, `CodeNavigationTarget.swift`) is the one rule for every user navigation to code except a terminal's ⌘-click (`Board.openCode`, its own preview): Go to's file/symbol/Recent rows (source nil), definitions (the code tile), changes-tile lines (`preview: true`, `extra: diffBase`), an HTML page's `code.open` and a note's `path:line` link. In order: the tile `Board.tileShowing(aim, near: source's frame)` finds anywhere on the board (a code tile, any author, not a follow tile, showing `aim.path` at exactly `aim.range`, else a captioned one whose range contains it; exact first, then in view, then nearest, then topmost): nothing changes and `CodeOpened.existing` is true, and the canvas goes to it (`CanvasView.goToShown`: selected, `Layout.present`; a definition inside the clicked tile scrolls it instead). A terminal's ⌘-click (`Board.openCode`) asks `tileShowing` first too; with `preview`, the tile this source created last (`codePreviews[source]`) while its `rev` is unchanged and it is still `isNavigationSurface`; a navigation-surface tile in view showing `aim.path`, nearest the source's center (the viewport's without a source); else a new code tile (`place(near: source, shrinkingTo: followMinimumSize)`, or at the viewport center), which becomes the source's preview with `preview`. `isNavigationSurface`: a code tile the user created whose last writer is the user, with no caption, no `parent`, no group listing it, no `followOf`. Re-aims are `Board.unrecorded` updates credited to the user (logged, never an undo step); the answer (`CodeOpened`) carries the `CodeReaim` (tile, `before`, `after` aims). Without a viewport (no window) every tile counts as in view.

Back/Forward (`NavigationHistory`, per `CanvasView`): `CanvasView.navigating(landing:_:)` wraps a navigation, recording `Entry(from:, to:, reaim:)` with the viewport before and after (nested navigations are one entry; one that neither moved the view, re-aimed nor changed a step's selection is dropped; 100 entries). An ⌥⌘-arrow step (`CanvasView.moveToNeighbor`) records its entry directly with `selectedBefore`/`selectedAfter`, and `Move.selection` selects that object again on Back/Forward and visiting `landing` in `RecentLocations` (20, newest first, one per path and start line; Go to shows 5). Back pops an entry onto Forward and shows `from`, re-aiming `reaim.tile` from `after` to `before` only while `Board.restoreAim` finds it still navigation surface showing `after`; Forward the reverse. A new entry clears Forward. The window takes ⌘[ / ⌘] ahead of the focused view (`CanvasWindowController.navigationAction`); with a browser page (not its address field) holding the keyboard they go to the page's `goBack`/`goForward`.

### Code tiles

One view per tile, no modes: the whole file (the base version for a deleted file), scrolled to `props.range`, the range tinted only while the tile shows rows outside it (`CodeMetrics.tintsRange`: a tile fitted to its range, or a whole-file range, shows no tint; live, cards, and renders alike). Geometry is `CodeMetrics` (CanvasCore): fixed 16 pt rows, the 12 pt system monospaced font (every column `charAdvance` wide, tabs to 4 columns, East Asian wide characters and surrogate pairs 2), a gutter of line numbers plus a sign column, and header/caption/history strip heights; `object.measure` uses the same numbers. Rows soft-wrap at the tile's text width (`CodeMetrics.textColumns`, `CodeMetrics.wrap`): a line wider than the text column continues on rows with no line number (a faint ↪ instead), its gitsign continuing down the gutter, and its text indented by the line's own indentation plus 2 columns (at most half the row); tabs expand against the unwrapped line and breaks never split a surrogate pair. Nothing scrolls sideways. A resize by the user rewraps live, keeping the top line in place; any other change of the tile's natural size (an agent's `object.update` frame or `size: "fit"`, undo) re-aims the scroll at the range by `CodeMetrics.scrollOffset` (`CodeTile.resizedElsewhere`, called by `CanvasView` when the content's size changed under it), so a fitted tile shows exactly its range. The model is CanvasCore's `CodeDocument` (built off the main thread from `GitDiffEngine`'s `FileDiff`): `GitSign`s from the diff's change records (added bar, modified bar, deleted wedge on the top edge of the line after the deletion, `lineCount + 1` at the end of the file), per-line highlight runs (`SyntaxLines`) for both sides, and the header's status and warning (`noBase`: no commits yet / no default branch / no merge-base, `diffTooLarge`, deleted). A file not in the base is `added` (every line an added bar; `untracked` when git doesn't track it yet: "new file, not tracked by git yet"), unless git ignores it (`git status --porcelain --ignored=matching` says `!!`, e.g. a node_modules frame): `ignored`, plain source with a quiet "ignored by git". The base picker names the base as the changes tile's does (`ChangesBaseChoice.title`: Uncommitted changes, Branch vs origin/main, vs <commit>); the status adds the base's commit unless the picker shows it (a commit typed as its sha), and `CodeDocument.baseDescription` (`against merge-base with origin/main b57db4f`) is the picker's and status's tooltip. `CodeRows` inserts peeked base lines above the lines that replaced them (entries: logical rows) and maps entries to visual rows (wrapped entries take several): `row(_:)`/`segment(_:)` give a visual row's logical line and slice, `index(ofLine:)` a line's first visual row, `rows(ofLine:)` all of them; `WrapText` measures each line's columns once per load so rewrapping skips lines that fit. Selections are `CodeRows.Position`s (entry + UTF-16 offset), so they survive rewraps and ⌘C copies logical lines; mentions, LSP positions, range tint, edit flash, peeks, hunk jumps, `reveal`, and `aim` all go through the same mapping, and cards, `render`, and the live view draw through one `CodePainter`. `CodeEdits.changes` diffs the texts of consecutive loads of the same file: those rows flash for 3 s (a follow tile also jumps to the first). A tile with `pinnedCommit` shows the file as of that commit instead (`GitDiffEngine.pinned`: `rev-parse` then `cat-file blob`, `FileDiff.State.pinned`, or `.pinUnavailable` with the reason as its notice): no signs, no base picker or change stepping, no Edit Here, header status `pinned at <sha7> (<revision>) · read-only`, and its mentions carry the commit (no side), so they quote those lines; `object.measure`, `layout.check`, and line anchors read the same text (`NoteSource.read` with the commit). `FollowLock` holds a follow tile's re-aims for 10 s after the user scrolls, clicks, or selects in it, counting them ("N new ▸"), then shows the newest.

Ranges stay on their code (`CodeAnchor`, `NoteAnchor.resolve`): a code tile with a `range` that isn't a follow tile or pinned to a commit re-finds its range whenever it installs a new text of the file (live reloads, and the reload before a render or card) or its `range`/`anchor` change: by the text the range held when the tile last found it (in memory), else `props.anchor` (the range's first line, trimmed). A range found elsewhere, or longer or shorter by lines inserted or removed inside it, is written back with its first line as `anchor` by `Board.reanchor`: bookkeeping like `writeBookkeeping` (no `rev`, undo step, or log; a board revision and `object.updated`), so agents, `layout.check`, measure and renders see the moved range and an agent's `object.update rev:` still holds. Undo restores `range` and `anchor` together, and the tile re-finds the range from there. A range whose code is gone keeps its lines, loses its tint, and the header shows "⚠︎ stale: …" before the status. An `object.update` (or any re-aim) that changes `range` or `path` without an `anchor` drops the old `anchor` (it named another line); an agent may pass `anchor` itself. `object.get` on such a tile adds `rangeStatus` (`AnchorStatus`): the tile reloads the file unless it is current (re-anchoring as above, and the returned `object` carries the result) and resolves the range with the text it last found there (`ApiRouter.codeRangeStatus`), so a first line repeated elsewhere never passes for it; without a tile, by `props.anchor` alone. Links are positions: `<canvas-link line=>`, `<canvas-code lines=>` and a note's `path:line` don't move with the code (`<canvas-code>` shows a stale badge when its `symbol` is lost); only ranges that anchor do.

The view draws only visible rows (a CTLine per visible row, cached only while visible) and scrolls itself, with no NSScrollView; not live, it keeps no line cache, layer contents, tracking areas, or views in the window, and cards, `snapshot()`, and `render(_:)` draw rows straight from the model.

Mentions: a row is the line on the side it shows; a sign in the gutter is the whole change (a deletion: its base lines, `side: old`); a peeked row is a base line (`side: old`, `commit` = the base). While a tile shows changes against a base, its new-side mentions carry `side: new` and that base's commit.

Follow tiles (`props.followOf`): `Board.follow` (`follow.report`) re-aims the terminal's one follow tile (at `range`, else at the hunk of `changes` spanning the most lines, the last of equals: `Board.followAim`; `changes` is kept as `props.lastChanges`, which the tile flashes when it loads the file fresh, and a re-load of the file it shows flashes whatever changed), creating it with `Board.place` beside the terminal (shrunk to stay wholly in view when the terminal is on screen, see Placement). Reports are ignored while the terminal's `props.follow` is `false`, and for paths `FollowFilter.follows` rejects: outside the board root, the terminal's cwd, and every other worktree of their repositories (`GitWorktree`: directories whose `.git` leads to the same common git directory, read from the filesystem, no git process; such a file keeps its absolute path, so the tile diffs it in its own worktree); under the temp directory (`NSTemporaryDirectory()`, `/tmp`, `/var/tmp`) unless the project containing it is there too; missing, a directory, larger than the code tile's limit (`GitDiffEngine.maxFileSize`, 4 MiB, by its size, unread), a binary extension (images incl. svg, pdf, archives, objects, media, fonts), or a NUL byte in the first 8000 bytes. The tile keeps its last accepted file. Deleting a follow tile other than by undo/redo sets its terminal's `props.follow` to `false` in the same undo step; `Board.setFollowing` (the terminal's "Follow Files" menu item) sets it back to `true` (the next report creates the tile) or to `false` and deletes the tile, one undo step. Deleting a terminal deletes its follow tiles in the same step. The history (`props.history`, newest first, at most `Board.followHistoryLimit` = 8) records each location with its action; a location revisited moves to the front and stays `edit`/`write` once edited, and past the limit the oldest reads go first, so every edit of a parallel burst (omp lands three edits within 50 ms) stays listed. The history strip (`CodeHeaderBar.fitStrip`) marks edit and write chips with a pencil in orange, always shows the current location, then the edits, then as many of the newest reads as fit whole, in history order; the oldest reads drop off a narrow tile first instead of the strip clipping or squeezing the current one. A re-aim to another file and back before the other file loaded (two reports a millisecond apart) still scrolls to the newest range when the load installs the same file (`CodeTile.rangePending`). A code tile whose file is on neither the disk nor its diff base (`FileDiff.State.missing`, checked again 0.6 s later so a delete-and-recreate save doesn't count) calls `Board.codeFileVanished` with the history paths found on disk: a follow tile steps back to the newest `history` entry still there (its `path`, `range` and `action` as `lastAction`, no edit flash) and drops the entries that are gone; with none left, or for a ⌘-click preview in `codePreviews`, the tile is deleted as a replay would (no undo step, and a closed follow tile doesn't turn its terminal's `follow` off); the activity log credits `system`. Other tiles are kept.

### Changes tiles

`ChangesTile` (`Sources/CanvasApp/Changes/`) draws a `ChangeSet` (CanvasCore) through `ChangesPainter`, live, as its card, and for `view.render`, with `ChangesMetrics`/`ChangeRows` geometry (header strip, the file list with more than one file, file rows, hunk rows, `CodeMetrics` line rows soft-wrapped at the tile's text width by `CodeMetrics.wrap` with the code tile's hanging indent and a faint ↪ in the gutter), which `object.measure` and `size: "fit"` use too (the file list open, deleted and viewed files folded, lines wrapped at the fitted width). The header of the file under the top of the rows stays pinned there while its hunks scroll (`ChangeRows.stickyFile`), pushed up by the next file's, and drawn over the rest of the file's last row when only a sliver of it shows above the next file. The header strip (`ChangesPainter.headerLayout`) holds the summary (`ChangeSet.lead`, drawn with ▾, then `counts`: `Uncommitted changes · 3 files · +40 −12`, `pr-1041 vs origin/main · 6 files · +62 −0`: the reviewed worktree's branch, or `HEAD` detached, against `baseName`), the keys when they fit beside all of the summary (`ChangesMetrics.hint`), and a filter field (an `NSSearchField` while live, drawn text in cards) that limits the list and the sections to files whose board path contains its text. A click on the lead opens the base picker (`ChangesBaseChoice`: `HEAD`, `merge-base` titled `Branch vs <GitWorktree.defaultBranch>`, the typed revision when current, and Commit or Ref…, a popover field); a pick is `object.update` of `props.base` by the user, one undo step.

Listing (`ChangeSet.load`, all through `GitRunner`, off the main thread): the reviewed directory is the board root, or `ChangesSpec.root` resolved against it when that lies in a worktree sharing the board repository's common git directory (`GitWorktree.sameRepository`, from the filesystem); any other `root` is refused (`notice`, nothing listed). `rev-parse --show-toplevel` from that directory; the base resolved as code tiles resolve theirs (`ChangesSpec`: `base` default `HEAD`); `paths` (default the reviewed directory) turned into repository-relative literal pathspecs, and anything resolving outside that worktree refused; `git diff --raw -z -M <base>` plus `git ls-files --others --exclude-standard` (untracked = added), at most 300 files (`omitted` counts the rest); each file's texts and hunks from `GitDiffEngine.diff` (a rename: the base text of its old path and `git diff -M -U0` between the two paths); hunk status from `git diff -U0` (index → working tree), `git diff --cached -U0` (HEAD → index) and, for a base older than HEAD, `git diff -U0 HEAD` (`ChangeHunk.status`: `partial` where the index differs from both the working tree and HEAD over the hunk, i.e. staged and edited again). Board paths are relative to the board root when under it, else absolute (another worktree's files). Hunk ids (`ChangeHunk.id`) hash the path and the unified lines (FNV-1a), so they survive line shifts elsewhere; a file's `fingerprint` hashes its hunk ids, status, and notice. The live tile reloads on `FileEvents` (FSEvents) under the repository's top level, and the worktree's own git directory when it lies elsewhere (a linked worktree's `<common>/worktrees/<name>`), ignoring the git directory except `index`, `HEAD`, `packed-refs`, and `refs/`, and on `.gitDiffBaseChanged` and `.reviewPatchApplied`.

Actions (`ReviewPatch`, `ReviewGit`): every Stage and Discard is one unified patch, applied with `git apply --whitespace=nowarn -` in the repository's top level (the reviewed worktree's), and its undo is the same patch applied the other way round (`-R` toggled). Patches only name repository-relative paths (no `..`, no `.git`, `ReviewPatch.checkPath`) of files the listing found, and never carry mode changes except a created or deleted file's own.

| Action | Patch | Applied | Undo |
| --- | --- | --- | --- |
| Discard hunk / file, base HEAD | base → working tree over the hunk's changes (all of a file's; a created file is its deletion, a deleted file its re-creation from the base; a renamed file keeps its name), 3 lines of context, from the texts the tile shows | `git apply -R` to the working tree (the index is untouched) | `git apply` of the same patch: the hunk comes back exactly |
| Discard hunk / file, base older than HEAD (`ChangeSet.includesCommits`) | HEAD → working tree changes (`git diff -U0 HEAD`, read at the moment and checked against HEAD's text and the working tree the tile showed) that touch the hunk's working-tree lines, or all of the file's; an untracked file is its deletion, a file deleted since HEAD its re-creation; committed hunks refused (`ReviewPatch.discardUncommitted`) | `git apply -R` to the working tree | `git apply` of the same patch |
| Unstage hunk / file | HEAD → index changes (`git diff --cached -U0`, checked against both texts) that touch the hunk's lines in the index (`ChangeHunk.indexSpan` through the index → working tree changes), or all of the file's; a file new in the index is its creation, a staged deletion its removal (`ReviewPatch.unstage`) | `git apply --cached -R` | `git apply --cached`: staged again |
| Stage hunk / file | index → working tree changes (`git diff -U0`, read at the moment of staging and checked against both texts) that touch the hunk's working-tree lines, or all of the file's; an untracked file is added whole, a file deleted from the working tree removed | `git apply --cached` | `git apply --cached -R`: the index is as it was (an added file is untracked again) |
| Discard / Stage / Unstage selected lines | the hunk's patch as above with only the selected changed lines (`ReviewPatch.LinePick`; a patch not built from the tile's own texts finds a selected line in the other version by its text in the change there, `ReviewPatch.matching`). Within a change the n-th removed and n-th added line stay paired. Forward (stage): unselected `+` dropped, unselected `-` turned into context; reversed (discard): unselected `-` dropped, unselected `+` turned into context; headers recounted | as the hunk | as the hunk |

A patch that doesn't apply (the lines changed since the tile read them, the index is locked by another git) changes nothing and the tile says so in its header (`ChangesFailure`); staging a hunk the index already holds is refused as `already staged`, unstaging one it doesn't as `not staged`, and discarding a committed hunk (`HunkStatus.discardable`; a file whose hunks are all committed, `ChangedFile.discardable`) as `committed: Discard only puts back work not committed yet`: the tile shows no Discard button there. Discard asks first, by key or click alike (`ChangesTile.askToDiscard`, one pending question naming the file, hunk id and picked lines): `r` asks for a second `r` within 2 s, a click on a Discard button turns it into a red "Discard?" for 3 s that a second click on it confirms (the header says how to go on); once applied, the canvas's notice says `Discarded <path>, lines 13–20 from your files · ⌘Z undoes` (`ReviewPatch.discardNotice`, undo's own naming). Unstage takes Stage's button once all of a hunk (or file) is staged; `u` unstages the selection or the current hunk. `ReviewGit` applies patches one at a time in the order asked, so an undo right after its action waits for it. `Board.recordReview` records an applied action as one undo step: the tile's `props.reviewed` entry (`ReviewPatch.entry`: action `stage`, `unstage`, or `revert`, path, scope `file`/`hunk`/`lines`, the hunk's `id`, `header`, `label`, counts, and the patch text, at most 200 lines; at most 100 entries, oldest first) and an `UndoEffect` named for it (`ReviewPatch.name`: `Stage of src/a.rs`, `Discard of src/a.rs, lines 15–46`, `Unstage of 2 lines of src/a.rs`) whose undo and redo apply the patch reversed and forward; one whose patch no longer applies is reported to the tile (`.reviewPatchFailed`) and leaves the files alone.

Viewed: the file header's check writes `props.viewed[boardPath] = fingerprint` (one undo step, dropping entries whose diff changed since) and folds the file; an entry counts only while the fingerprint matches (`ChangedFile.isViewed`), so a changed file unfolds on the next listing. Fitted tiles (`ChangesMetrics.grown`): after a reload, a tile whose natural height equals `ChangesMetrics.fit` of the previous listing (at its width) grows to the new fit when that is taller (`Board.growFitted`: credited to the system, never an undo step); one sized for an empty listing (or none yet, after a relaunch) grows wider too, a tile the user made (Review Changes: a compact "No changes" when it first lists nothing) to at most the default 820×620. Review Changes (the canvas menu's per-worktree Uncommitted changes and Branch vs <default branch>, File › Review Changes and Review Branch) lists first (`ChangeSet.load`) and then creates the tile, compact when nothing is listed. `object.create` of a changes tile by an agent (`caller`) that already made one on that board for the same `root` (resolved), `base`, and `paths` is `object.update` of that tile with the call's other props, `frame`, and `size`, and answers `reused: true` (`ApiRouter.reusableChanges`; not in batches).

Scrolling: a trackpad gesture belongs to whoever its first movement picks (the tile when it can scroll and the movement is mostly vertical, else the canvas) until it ends, momentum included; a gesture's first event without movement never reaches the canvas while the tile can scroll, so the canvas can't start tracking a gesture that turns out to be the tile's. Wheel notches and phaseless steps go one by one, as in code tiles. j/k, J/K, ]/[, s/r scroll the current hunk into the tile's view below the pinned file header (`reveal`), never the canvas.

Opening code: a click on a line opens it by `Board.openForNavigation` with `preview: true` (the tile's own preview, else a plain code tile in view showing the file, else a new one beside the tile, shrunk down to a follow tile's minimum to land wholly in view; see Navigating to code), one step of Navigate Back; then the canvas pans the least that shows it together with what showed of the changes tile (`Layout.reveal(_:keeping:…)`, the padding cut to the room left when both just fit), or the code tile alone when both can't fit.

Mentions: a diff line is a `code` mention of its side's line (`side: new` for context and added lines, `side: old` with the base's name of the file for removed ones) with `commit` = the base and `diff` = what it is (`ChangeSet.mentionDetail`: `added|removed|context line · unstaged|partly staged|staged|committed hunk`); the prompt names the side either way (`, new side (working tree)`, `, old side (base)`). A hunk header mentions the whole hunk (`ChangeHunk.mentionLines`, `diff`: `whole hunk +a −r · unstaged|partly staged|staged|committed`); a file header mentions the tile. The header's hints (`ChangesMetrics.hints`) leave out staging and Discard for a listing with nothing to stage, unstage or discard (`ChangeSet.actionable`: a branch's commits only). The tile's keys (`ChangesTile.key`) act only once it has the keyboard; pressed while it is only the selection, `keyWhileSelected` says "press ↩ first to use the tile's keys" in its header, and the drawing layer leaves them alone (`ChangesTile.isOwnKey`: `r` there never picks the rectangle tool).

### Image tiles

`ImageTile` shows `props.path` (board-relative, absolute, `~/…`, or a `file://` URL: `LocalImage.tileFile`; any file the agent or user names, unlike notes and pages) decoded by `NSImage` (bitmaps, SVG, a PDF's first page), read off the main thread, aspect-fit and never scaled past its natural size above the optional one-line `caption` strip (`LocalImage.captionHeight`). While live it watches the file's directory (`FileEvents`) and reloads on any change to the file, so a chart re-saved in place, or one written after the tile was created, shows; not live, it reloads when it is again. `view.render` and cards draw from the loaded picture. Natural size is one point per pixel for bitmaps (`LocalImage.naturalSize`, from the header only), the document size for SVG and PDF; `object.measure`, `size: "fit"`, and a create without a frame height give the picture at most `width` (default `LocalImage.defaultMaxWidth`, 960) wide plus the title bar and caption. A Hyper-click on the picture mentions `.image(object, path, x, y)` in image pixels; elsewhere the tile.

## Export

The object menu's Copy as Image and Save as PNG… draw the selection with `view.render` (`CanvasView.render`, `.objects(selection)` plus every group whose members are all selected, `SelectionScope.export`, at 2 px/pt: tiles, drawings and groups under it, no app chrome) with `RenderRequest.chrome` false: as View › Hide Canvas Chrome shows the board, without author marks, close glyphs or the dot grid (a plain canvas background; `view.render` itself keeps them). They put the PNG (plus TIFF) on the general pasteboard, or write it where a save sheet says (default: the folder last saved into, `canvas.exportDirectory` in user defaults, unless it is gone or inside the board root; else `~/Downloads`; name `ExportFile.name`). An HTML tile adds Save as HTML… and Open in Browser (see HTML tiles). Save panels run out of process, so replayed input can't type into them; `input key return` on one saves under its suggested name.

A browser tile's Snapshot to Image (its object menu; File › Snapshot Page to Image for the focused or selected one; `CanvasView.snapshotPage`) takes the page as it shows (`WKWebView.takeSnapshot`, the screen's pixels; a released page its last capture), writes it as a PNG under the board's directory (On-disk locations) and creates an image tile with its absolute path, titled `<tile title> · <time>` and captioned with the page's address, as wide as the browser tile (`ObjectMeasure` image size), placed beside it (`Board.place`) and selected. Deleting the tile leaves the file, so ⌘Z brings it back whole.

## Drawing layer

`.shape` and `.arrow` objects are drawn by `ShapeLayer` (`Sources/CanvasApp/Drawing/`), one view in document coordinates above every tile and below the Hyper outline. Geometry lives in `Sources/CanvasCore/Drawing*.swift`. Selection and moves of drawn objects are the scene's (see Scene seams); the layer supplies rendering, hit tests, outlines, resize handles, tools and editors, arrow routing, and region images.

- A shape's `frame` is exactly its drawn box (no title bar). Ink `points` are relative to the frame origin; the frame is the painted stroke bounds.
- An arrow's route is derived, never stored: bound ends attach to the facing edge of the bound object's current outline (a tile's frame, a shape's frame, the curve of an ellipse), so arrows follow moves and resizes without writes. An end bound to `lines` of a code tile is a row end (`ArrowEnd.row`): it attaches to the tile's left or right edge (right unless the other end lies wholly left) at the first visual row of `lines.start` (wrapped lines above it push it down), `CodeMetrics.lineY`: live, the tile's rows as scrolled (`CodeTile.lineY`; the tile posts `CodeTile.rowsMoved` and the layer re-routes), and in the model (`BoardGeometry.routes`, `layout.check`) the tile freshly aimed by `CodeMetrics.scrollOffset`, the same rule `CodeTile` scrolls by (range start with up to 3 rows of context, fewer when the viewport can't show them and the range). A line out of view clamps to the top of the rows or the bottom of the tile. Orthogonal routes with a row end leave sideways, looping around the right edges when the two tiles overlap horizontally; `avoid` uses only the two side ports. `lines` on other tiles binds the whole tile. `DrawingGeometry.path` (CanvasCore) routes by `props.route`: `straight`, `orthogonal` (one jog between facing sides), or `avoid` (an orthogonal grid search around every object `BoardGeometry.blocksRoutes`: tiles, text, filled shapes, keeping `avoidMargin`). Arrows bound to the same two objects in either direction get `parallelOffsets` (`parallelSpacing` apart, relative to each arrow's direction, so opposite arrows take opposite sides); labels go beside the route on the offset's side (`labelRect`), at the first spot clear of tiles. The caption is `label`, else `relation` in the secondary color when `label` is absent; `label: ""` draws none (`DrawingStyle.arrowLabel`). The layer draws, hit-tests, and selects the routed polyline; `BoardGeometry.routes()` computes the same routes from frames for `layout.check` and detaching. An arrow's `frame` records its route bounds when it was drawn. Free ends (`{"point": [x, y]}`) are canvas coordinates. Deleting a bound object turns that end into a free point where it last attached, in the delete's undo step, so the arrow keeps its direction and its other end keeps following.
- The frame the API reports for an arrow (`board.get`, `object.get`, create/update results, `board.history` summaries; `Board.reported`) is the bounds of its routed line: as drawn (`Board.arrowPath`, supplied by the drawing layer), else routed from object frames (`BoardGeometry.routes(only:)`). The stored frame of an arrow with a bound end is a meaningless placeholder.
- The layer never takes keyboard focus (it stays with the prompt-target terminal); tool keys V/R/O/A/T/P/Esc arrive as key equivalents and only act when no terminal or text view has the keyboard. Inline text and arrow editors take focus while open and give it back on Enter/Esc/click-away, never over a responder that took focus meanwhile. The text editor (`ShapeTextEditor`) commits on Enter, Esc, and click-away (an emptied text shape is deleted; the arrow caption editor's Esc cancels), and draws a steady caret itself in a window that isn't key. A text shape's size follows `TextShapeLayout` (CanvasCore): a frame exactly as wide as its grown text keeps growing up to `autoWidth` (320) × scale as it's edited, any other width is its wrap width. An arrow end binds to the topmost shape (within the hit tolerance) or tile under it, else the nearest shape, else the nearest tile, within `ShapeLayer.arrowSnap` (16 screen points).
- Only strokes, text, labels, and fills (`fill: semi|solid`) take the mouse; an unfilled shape's interior passes clicks to the tiles beneath.

## Scene seams

`CanvasView` (`Sources/CanvasApp/CanvasView.swift`) owns selection, moves, groups, attention markers, and the viewport. Drawn objects (shapes, arrows) have no view of their own; the drawing layer plugs in through:

| Seam | Direction | Meaning |
| --- | --- | --- |
| `installShapeLayer(_:)` | drawing → scene | Adds the drawing layer above tiles, below attention markers and the overlay; restacking keeps it there. |
| `shapeHitTest(docPoint) -> ObjectID?` | drawing → scene | Drawn object under a point (strokes, text, fills). Plain clicks there select it and drag the selection; Hyper-clicks mention it. |
| `shapeOutline(id) -> NSRect?` | drawing → scene | Committed document rect, for rings and hover outlines. |
| `drawingOwnsPoint(docPoint) -> Bool` | drawing → scene | True while a tool is active or over a shape handle; scene selection, marquee, and moves stand down. |
| `moveProps(object, dx, dy) -> JSONValue?` | drawing → scene | Props merged into a drawn object's move update (e.g. free arrow endpoints). |
| `onSelectionDrag(ids, offset)` | scene → drawing | Live drag offset in document points; `.zero` just before the move commits. |
| `selection`, `onSelectionChange` | scene → all | Current selection (tiles, drawn objects, groups). |

Groups (`type: group`, props `{members, title?, color?, padding?}`, frame derived by the board, see Object model rules) are drawn by the scene as titled, tinted regions behind their members (`GroupView`), following members live mid-drag with the same `GroupSpec.frame`; only the title band takes the mouse. Title and border are in document space like everything else. `focus(tile:)` zooms a tile to 100%, centers, selects, and focuses it. Attention markers are board state (`Board.attention`, `Attention.swift`): `view.attention` raises and clears them in CanvasCore, the scene shows what the board holds (`attention.changed` events, and the stored markers when a board opens), and every user acknowledgment (selecting, focusing, clicking the bubble, an edge pill, looking a while) is `Board.clearAttention`; the empty canvas's Clear Attention Markers is `Board.clearAllAttention` (markers aren't undo history). `CanvasView.layoutPills` places every bubble and edge pill in one pass (`PillLayout`, CanvasCore: bubbles above their object, else on its title bar, never on another pill nor on a blocked terminal other than their own; edge pills slide along their edge, off blocked terminals where it has room), for markers and for terminals whose lifecycle is `blocked` (ring and bubble, or edge pill, in the blocked `AttentionStyle`: orange with a raised hand before the lifecycle message; markers are pink; blocked bubbles are placed first; they appear and go with the lifecycle state, and clicking one selects the terminal and gives it the keyboard), on every pan step, object move, and scene pass. A board's tab shows `NeedsYou` (CanvasCore: blocked beats done, nothing for working or idle), refreshed by the window controller on terminal updates. Every user viewport jump (`go(to:)`, `zoomToFit()`, `zoomToActualSize()`, `focus(tile:)`, `jumpToAttention(_:)`, `reveal(_:)`, entering a group, opening a board) aims at the clear area between the floating toolbar and the tray (`chromeInsets`, measured by the window controller, plus a 12 pt margin); the geometry is `Layout.fit`/`center`/`reveal` (CanvasCore).

## Undo

`Board.history` records every create, update, and delete from any actor; ⌘Z (`Board.undo()`) reverts the latest step even when an agent made it, never silently: each step (`UndoHistory.Step`) records its author (the agent when an agent made any of it, else the user), `Step.summary` says what it did by verb and object type (`created 9 code tiles, 6 arrows; moved a note`: updates of objects the step created or deleted are part of that; a group re-fitted or an arrow re-routed is left out beside anything else), and `Step.title` names it for Edit ▸ Undo/Redo (`Undo Create 9 Code Tiles, 6 Arrows (omp)`, the author by `Board.authorName`: the terminal's `name`, else its agent's kind). Undoing or redoing an agent's step, or any step with an `UndoEffect` (a change to the files or git index), shows a HUD above the tray for 4 s (`Step.notice`: "Undid omp: … · ⇧⌘Z redoes", "Undid Stage of src/regex_helper.rs · ⇧⌘Z redoes"; `UndoHUD`, also announced to VoiceOver); an effect's name leads `Step.summary` and `Step.title`. ⌘Z and ⇧⌘Z stay with a terminal holding the keyboard (Edit ▸ Undo/Redo disabled then). Navigation's re-aims are never steps (`Board.openForNavigation`). and every undo or redo is a new revision, newer than any the object ever had, even across a delete and re-creation. Bookkeeping nobody chose is never an undo step and never rewound (`UndoHistory.bookkeeping`, `Board.unrecorded`, `Board.writeBookkeeping`), so ⌘Z reaches the user's last own action through an agent's work: a terminal's `lifecycle`, `agent`, and `title`; a browser's `pageTitle` (the page's own title; `title` is the creator's and stays undoable); a follow tile's `path`, `range`, `lastAction`, and `history` (every `follow.report`), and the follow tile appearing; and every update the app writes back as `system` (a note's resolved `anchor=`). An undo of an earlier step keeps them as they are now (a moved follow tile goes back, still aimed where its agent last looked), and undoing a terminal's creation takes its follow tile along. Multi-object gestures wrap their updates in `Board.transaction { }` to form one step; API writes that must succeed or fail together (`object.batch`, `layout.*`) use `Board.atomically { }`, which also rolls back on error. Repeated updates of one object within a step collapse into one recorded change (first before, last after), never across an `atomically` mark. Undoing a delete restores the object with the same id and `z`; staged mentions of it are not restored. When undo/redo removes a terminal and later brings it back, it returns with the bookkeeping it last had. History lives in memory only. A step can also carry an `UndoEffect`, a change outside the board run on undo and redo (a changes tile's `git apply`, see "Changes tiles"); its slow work runs in a task of its own, so undo itself never waits on git.

## Mention context format

`tray.drain` returns a `context` string that the omp extension injects as hidden context with the submitted prompt. The tray's mentions belong to the terminal it shows, the board's prompt target (`CanvasView.promptTarget`, settled by `CanvasWindowController` from `PromptTarget.choose` over what the rule remembers, `Board.promptTarget`: terminals in focus order and the tray menu's pick, saved in the board file as `promptTarget` so the target survives a restart; the router reads it through `viewState`): a drain whose `caller` tile is another terminal returns no mentions, an empty context, and `held`/`target`, and changes nothing. A drain without a caller, or on a board without a window, takes the tray as before. Worktree affinity (`PromptTarget.affinity`, applied by `CanvasWindowController` when a mention is staged): a mention whose file lies in another checkout than the current target's working directory (`PromptTarget.checkout(of:)`: a code line's or image's file; a whole code or image tile's file, a changes tile's reviewed worktree, a note's or HTML tile's link root; checkouts compared by git directory; a terminal's is where its shell last reported, else `props.cwd`, else the board root) moves the target to the one terminal running an agent in that checkout, as if it had been focused last; with none or several there, the target stays. The tray line then reads `→ <name> · works in <checkout directory>` until the target changes. A drain with a caller also gets the mentions other agents attached for that terminal with `agent.prompt` `mentions` (`Board.handoffs`, in memory, never in the tray), after the tray's and numbered on from them, in one block per sending terminal: `<canvas-mentions board="…" root="…" from="obj_…">` whose first line is `Attached by terminal obj_… "name" to its prompt to you (agent.prompt):` (the name as the tray shows it; `Attached by a script …` without a caller); `tray.commit` removes them like tray mentions, and deleting a mentioned object or the terminal drops them. Hyper-V (Edit ▸ Paste Mentions into Terminal) drains with the prompt target as caller, pastes the context plus a newline as one bracketed paste without Enter, and commits those mentions once the paste went in. Hyper-click on a drawn object mentions the whole selection when the object is part of a selection of several, else every member of a group made only of drawings (a `group` mention named by its title), else the object (`MentionContext.drawingTarget`); the Hyper outline shows the same set.

## Note fences

A note's `markdown` is plain markdown; the code fence info string selects how the tile renders a fence (parsed by `NoteFence` in CanvasCore):

| Info string | Renders |
| --- | --- |
| `ts file=src/app.ts#L10-40` (`#L10`, `#L10-L40`; no range = whole file) | Live excerpt of the file with line numbers |
| `ts symbol=restoreSnapshot` / `swift file=Sources/Board.swift symbol=Board.update` | Live excerpt of the declaration (best-effort, language-agnostic; `Outer.inner` searches inside `Outer`; without `file=`, the first tracked file that declares it) |
| `… file=src/app.ts@1a2b3c4#L10-40` | Excerpt pinned to a commit (`git show`) |
| any anchored form plus `propose` | The fence body as a diff against the resolved range |
| anything else | Free-written (authored) code; `path:line` references in it open code tiles |

Anchor resolution (`NoteAnchor.resolve`, shared with code tiles' ranges), in order: a symbol that resolves wins (`Outer.inner` searches the whole extent of `Outer`, however long; the declaration's own range stops at 400 lines; a signature's parameter list, over several lines, and braces inside it open no body, so Python's `) -> T:` line is followed by its indented body); otherwise the line range is re-found by the text the tile captured when it first resolved it (when that opens with the fence's `anchor=`, else by the `anchor="first line text"` alone), preferring the candidate whose following lines match best and the written position on ties; with the first line gone, by most of the captured text still standing together; else by the fence body (a proposal's own lines vote for where they sit). Captured text also carries the range's end: the shortest stretch from the start keeping as much of it as a generous window does, so lines inserted or removed inside the range move its end with them (lines gone from its end leave it shorter, unless the next line reads like the one it replaced); with only an anchor (after a restart) the range keeps its written length. A range that moved or changed length renders with "was L…"; one that can't be found renders a **stale** badge over the last text it showed.

A `propose` fence whose body the file already reads, contiguously and overlapping the resolved range (anywhere in the file when the anchor is lost, for a body of two or more lines or one found once), is **applied** (`NoteAnchor.applied`): it renders the file's lines with a quiet "✓ applied" and no diff. Not while the range's original text (captured, else the range as written) still stands whole around it: a proposal that only drops lines reads as part of its range until it is applied.

`object.get` on a note adds `fences`: per anchored fence (fences with the same info string are one), its `info`, `markdownLines`, `path` (as found by a symbol search), `symbol`, `commit`, `propose`, and `AnchorStatus`: `state` (`live`, `relocated`, `stale`, `applied`, `missing`), the resolved `range`, the `written` range when relocated, and the stale `reason`. The note tile resolves them against disk at that moment with the text it captured (`ApiRouter.noteExcerpts`), and shows the result; without a tile they resolve from the markdown alone. A note that isn't live watches nothing, so `view.render` of it resolves every fence first too; a live note with nothing pending draws what it resolved.

The tile writes anchors back: when a line-range fence without `anchor=`, `symbol=`, or a pinned commit first resolves, it appends ` anchor="<first line>"` to the fence's info string in one `object.update`, so anchors survive restarts and agents see them. It skips first lines that can't be written (blank, or a backtick inside a backtick fence) and falls back to the in-memory capture. `commit=` must name a revision (`abc1234`, `HEAD~2`, `v1.0`); anything shaped like an option makes the fence stale.

Hyper-click on an excerpt or proposal row mentions `code` (object = the note, the row's real path and line, and `commit` for a pinned fence; an added proposal row mentions the line it would be inserted before, or the file's last line when appended at the end of the file). Any other rendered paragraph mentions the markdown block it came from (`MentionTarget.note`, found by `NoteItem.at(line:in:)` from the paragraph's `.noteMarkdownLine`): the innermost list item containing it (with its nested items), else its outermost blockquote, else a fence, table row (the delimiter row stands for the header), or paragraph; a top-level heading takes its section, up to the next heading of the same or a higher level. The target carries the block kind, its heading path (top-level headings above it, levels may skip), its lines, and its markdown as it read (common indentation removed, cut to 40 lines and 2000 characters). The title bar, margins, blank space, and thematic breaks mention the note (`object`).

Code mentions carry the commit their lines are read against (`MentionTarget.code.commit`, schema `MentionTarget`): with `side: old` or no side, the commit whose version of `path` holds the lines (peeked base rows, deleted files, pinned excerpts); with `side: new`, the base the working-tree lines were diffed against; absent, the working tree. The context line names it from the mention alone, never from what the tile shows at drain time: `· diff vs merge-base 1a2b3c4` (the kind word comes from the tile's `diffBase`), `· diff vs merge-base 1a2b3c4, old side` for peeked base rows with the excerpt read by `git cat-file blob <commit>:<path>`, and `· at 1a2b3c4` for a pinned excerpt without a side. `tray.drain` is therefore asynchronous.

Link roots (`LinkRoot.swift`): a note's relative paths (fence `file=` paths, `path:line` and markdown links, `![alt](path)` images) and an HTML tile's (`code.excerpt`, `code.open`, `<img>`) resolve against the tile's `props.root` (absolute or board-relative, like a changes tile's `root`), else the board root. `object.create`/`object.update` accept only an existing directory in the board's checkout or another worktree of its repository (inside the board root for a board outside git; `invalid_params` otherwise; empty or null clears it). A note or HTML tile an agent creates (`caller` a terminal) without `root` gets the caller's checkout when it is another worktree of the board's repository, at the board root's place in it (`Board.defaultLinkRoot`; the caller's directory is where its shell last reported, else `props.cwd`), so a worktree agent writes `tests/x.ts:16` instead of `../wt-x/tests/x.ts:16`. Anchoring, `size: "fit"` and `object.measure` use the same root. A link opened from the tile names its file as the API stores paths (board-relative under the board root, else absolute).

## Git

All git in the app runs through `GitRunner.shared` (CanvasCore), which caps concurrent git processes at two, can cap stdout (`maxOutput`) and run time (`timeout`), feeds stdin (`input`, e.g. a changes tile's patch for `git apply`), stops git when the calling task is cancelled (a request still waiting for a slot just leaves the queue), and sets `GIT_OPTIONAL_LOCKS=0` so reads never contend with agents for the index lock. The only writes are a changes tile's Stage (the index) and Revert (working-tree files), each on the user's click or key, inside the tile's repository. Git, file reads, and parsing run on GCD (`offPool`), never blocking a Swift concurrency thread. Code tiles diff through `GitDiffEngine.shared`: live tiles `retain(containing:)` their repository and `release` it when they go offscreen or away; held repositories keep resolved bases and an FSEvents stream that posts `Notification.Name.gitDiffBaseChanged` (object: the repository's top-level path) when a commit, checkout, rebase, or fetch moves a base.

## HTML tiles

- Each tile's page is `canvas-kit://html/<tileId>`, served by the tile's own scheme handler: the kit head (`resources/kit/canvas-kit.css`, `canvas-kit.js`, `vendor/tailwindcss-browser.js`) followed by `props.html`. `/kit/…` serves `resources/kit` (Mermaid loads from there only when a page has diagrams). DOM mentions of HTML tiles use that URL.
- Images: any other request path the handler serves as an image file (`LocalImage.pageFile`), read off the main thread, never cached: the file at that path under the tile's link root (`<img src="out/fig.png">` resolves to `canvas-kit://html/out/fig.png`), else the absolute path it spells (`<img src="/tmp/…/fig.png">`), each only when it has an image extension (png, jpg, jpeg, gif, webp, heic, heif, tif, tiff, bmp, svg, pdf) and lies, symlinks resolved, inside the board root or a temp directory (`NSTemporaryDirectory()`, `/tmp`, `/var/tmp`). Everything else is 404, and `file:` URLs stay blocked by the rule list, so a page never reads other files on disk. A board directory named `kit` is shadowed by the kit.
- Export (the object menu's Save as HTML… and Open in Browser, `HtmlTile.exportDocument`): the page loads offscreen as for `view.render`, and once settled its DOM is serialized with each `<img>` inlined as a `data:` URL, the kit stylesheet inlined, and every script removed (Tailwind's generated styles, `<canvas-code>` rows and Mermaid diagrams are already in the DOM), so the file opens anywhere. Open in Browser writes it to `$TMPDIR/canvas-exports/<tileId>-<title>.html` and opens it with the default browser (with `CANVAS_NO_ACTIVATE` it only logs the file).
- Sandbox: non-persistent website data store per tile; a WKContentRuleList (WebKit's default rule list store, identifiers `canvas-html-<hash>`) blocks `http(s):`, `ws(s):`, and `file:` except `props.allowNetwork` hosts: `host` (any port), `host:port` (that port only; `:443`/`:80` also match the scheme's portless URL), `*.host` (the host and its subdomains). Exceptions pin the whole authority (no userinfo); other entries are ignored. A tile never loads with rules compiled for an allowlist that has since changed. The main frame never navigates away from its page; popups are refused.
- The only native access is the `canvas` script message handler (`window.webkit.messageHandlers.canvas.postMessage(msg)` → promise), accepted from the tile's own top-level page only. Each tile runs at most 4 messages at once with 64 more queued; beyond that a message is rejected (`too many outstanding requests`), and outstanding work is cancelled when the page re-renders or the tile detaches. Messages are strict (`Sources/CanvasCore/HtmlMessage.swift`: known `type`, only its fields, 64 KiB per message):

| `type` | Fields | Reply |
| --- | --- | --- |
| `code.excerpt` | `path`, `lines?` (`"N"`/`"N-M"`), `symbol?` | `SourceExcerpt` (`start`, `end`, `lines`, `language`, `stale`, `reason`, `truncated`) |
| `code.open` | `path`, `lines?`, `symbol?` | `{tile, created, existing}`: `Board.openForNavigation` from the HTML tile (a code tile anywhere already showing those lines, exactly or as a captioned stop whose range holds them: `existing`; else a plain code tile in view showing `path` re-aimed, never an agent's, captioned, grouped or follow tile; else a new one beside the HTML tile); from the live page (a user's click), the canvas goes to an existing tile (selected, centered when not in view) and pans the least that shows any other clear of the chrome |
| `state.get` | `key?` | `{value}` from `props.state` |
| `state.set` | `key` (`[A-Za-z0-9_.:-]{1,128}`), `value` (≤ 16 KiB, `null` deletes) | `{}`; `props.state` is capped at 256 KiB |
| `view.rendered` | `scrollY?` | `{}`; the tile refreshes its snapshot and remembers the scroll; the first after the page attaches lifts the card (`whenLiveReady`) |

- Paths are relative to the tile's link root (`props.root`, see Link roots; default the board root); absolute paths, `~`, `..`, and symlinks resolving outside it are rejected. `code.open` names the file as the API stores paths: board-relative under the board root, else absolute (a file in another worktree).
- `<canvas-code>` (canvas-kit.js/css) draws an excerpt's lines like a code tile: long lines soft-wrap at the element's width, continuation rows indented by the line's own indentation plus 2 columns (tabs as 4, at most half the row), never clipped or scrolled sideways.

Notes show `![alt](path)` images by the same rule as pages (`LocalImage.sandboxed`: relative to the note's link root, or an absolute path or `file://` URL inside it or a temp directory), read off the main thread (`NoteImages`) and drawn by the text layout at their pixel size, scaled down to the text width (`NoteImageAttachment`); a note watches their files and redraws when one changes. Anything else shows `[image: alt]`. `object.measure` and `size: "fit"` lay the images out the same way.

## Agent prompts and replies

`agent.list`, `agent.prompt`, `agent.wait`, and `agent.read` describe a terminal with one entry shape (`ApiRouter.agentEntry`, schema `Agent`): `tile`, `board`, `root` (that board's root directory), `name`, `kind`, `sessionId`, `lifecycle`.

`agent.prompt` refuses (`conflict`, unless `force`) a target whose agent reports a lifecycle while its terminal's foreground program (`TerminalStatus.program`, from the process table) isn't that agent (`PromptTarget.foreignProgram`: none of the program's words, extension dropped, is the agent's `kind`): an editor or a pager would take the text. For tmux it asks the client's own server (`ForegroundProgram.tmuxPane`: its binary, `-L`/`-S` and `TMUX_TMPDIR`, `display-message -c <the client's tty> '#{pane_pid}'`) what the active pane runs, and sends when that is the agent; another program there (vim, the pane's shell) is the conflict, named; when tmux doesn't answer, tmux itself is. Into a shell at its prompt (the session's shell known, nothing in the foreground) a one-line text of printable characters is typed (`ShellTyping`: Ghostty's `text:` action, one write, no bracketed-paste markers) instead of pasted: once, after 12 idle minutes, zsh ran a pasted command as `[200~clear…~`, most likely its line editor taking the paste's leading ESC apart from `[200~` (KEYTIMEOUT). Ghostty writes the start marker in one write and zmx forwards it in order (that session's zmx log shows the tile's client leader throughout), so the split happened past Canvas; typing leaves no ESC to split. It reads the target's session text (the last 400 lines, `TerminalTail`, each line with its position in the whole text) before it pastes, and keeps it in memory per terminal until the next prompt, the tile's deletion, or an app restart. `agent.read` `since: "prompt"` reads the last 2000 lines and returns them from the first remembered line that now reads differently (`TerminalTail.Tail.boundary(after:)`: a shell's prompt line that got the command, a TUI's input box its reply overwrote), else from where the old text ended. The scrollback's own trimming can move positions; the reply then starts earlier, never later. A terminal whose lifecycle is `unknown` gets no pending-prompt state, so `agent.wait` on it fails at once instead of waiting for a report that never comes.

`agent.prompt` `mentions` (`HandoffMention`, schema `PromptMention`: `object`, optional `lines` for a code tile, `point` for an image tile) become the `MentionTarget` a Hyper-click on the same place stages: a code tile's lines (its `range` when no lines are given) are `code` at the tile's `pinnedCommit`, with its `symbol` only for its own range; an image tile's point is `image`; anything else is `object`; lines or a point on another type are `invalid_params`. The objects must be on the target terminal's board, and the target must report a lifecycle (`PromptTarget.runsAgent`), else `unavailable`. They are queued (`Board.handOff`, duplicates of a waiting target skipped) before the text is pasted, so the drain of that very prompt finds them, and withdrawn if the paste fails.

`agent.report` `final` (only with `idle`) is the final assistant message of the turn that just ended: omp's extension takes the text parts of the last assistant message in `agent_end`'s `messages` (when it doesn't continue), the hooks take `last_assistant_message` from `Stop` (Codex, Claude Code) or `prompt_response` from Gemini CLI's `AfterAgent`; opencode sends none. `Board.finalAnswers` keeps it per terminal in memory until the next turn starts (lifecycle to `working` from idle, done, or no state) or the tile is deleted; stale-`seq` reports are dropped with their answer. `agent.read` `final: true` returns it as `text` (with `lines`), and fails with `unavailable` while an `agent.prompt` to the terminal hasn't started, while it is `working` or `blocked`, and when no answer is kept.

`agent.report` `error` (only with `idle`) says the turn ended on an error instead of finishing: omp's extension sends the last assistant message's `errorMessage` when its `stopReason` is `error` ("Anthropic stream error (overloaded_error)"), `interrupted` for `aborted`, and `stopped at the output token limit` for `length`, beside whatever `final` text it got. `Board.turnErrors` keeps it with the answer (cleared together); the lifecycle stays `idle` with it as the message (never `done`), `agent.read` `final: true` adds `cutOff` (the error) to a text that is the answer as far as it got, and with no text fails `unavailable` naming the error.

## Lifecycle authority

- The omp extension is authoritative for omp tiles (`source: "canvas-omp"`). It reports `blocked` while omp waits on its user: an approval dialog (`approve <tool>?`) or the `ask` tool (its first question). omp's `tool_approval_requested` event comes only from its registered-tool wrapper; eval preludes (the `browser` and `computer` globals inside `eval`) ask for approval with no event, so the extension wraps `select` on the session's UI context (the object behind `ctx.ui`, which tools and preludes prompt with) and treats each dialog titled `Allow tool: <name>` as an approval until it settles. It depends on that title; an omp that renames it reports no approval blocking.
- The Claude Code, Codex and Gemini CLI hooks and the opencode plugin ("Agent integrations") report with `source: "canvas-claude"` / `"canvas-codex"` / `"canvas-gemini"` / `"canvas-opencode"`.
- A report with a lower `seq` than the last accepted one from the same source is ignored.
- `done` is derived by the app: an `idle` report on a tile that has not been seen since it was last `working`.

## Ownership rules for slices

- The schema file is the only place API shape changes. Changing it means regenerating clients (`bun scripts/gen-clients.ts`) in the same change.
- Swift model types mirror the schema; a slice that needs a new field adds it to the schema first.
- No slice introduces a new socket, environment variable, or on-disk location without adding it here.
